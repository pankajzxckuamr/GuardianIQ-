**Yes.** AI Agents are explicitly modeled as first-class actors distinct from human users.

Based on my inspection of the Phase 2 workflow implementation (specifically within `workflow_execution/models.py` and `workflow_scheduler/models.py`), here are the findings regarding traceability:

### 1. Do 'schedule', 'run', 'output', and 'failure' entities exist?
**Yes, all four entities explicitly exist** and are richly modeled for Phase 2:
*   **Schedule:** `Phase2WorkflowSchedule` (`workflow_schedules`)
*   **Run:** `WorkflowRun` (`workflow_runs`) — also includes a child `WorkflowRunStep` (`workflow_run_steps`) for granular execution tracking.
*   **Output:** `WorkflowRunOutput` (`workflow_run_outputs`) — tracks findings, recommendations, severity, risk score, etc.
*   **Failure:** `WorkflowRunFailure` (`workflow_run_failures`) — tracks failure types, retry counts, escalation status, etc.

### 2. Do runs reference which agent/model/tool executed them?
**No, not directly via Foreign Keys.** 
Neither `WorkflowRun` nor `WorkflowRunStep` contains a foreign key to `agent_id`, `model_id`, or `tool_id`. 
*   Traceability at the individual execution (Run) level relies entirely on unstructured JSON blobs (`context_json` or `result_json` in `WorkflowRun`, and `input_json` / `output_json` in `WorkflowRunStep`). 

### 3. Is there a join table connecting agents/models/tools to workflows?
**Yes, but it exists at the *Schedule* level, not the core Workflow or Run level.**
There is a dedicated join table called `WorkflowScheduleAgentAssignment` (`workflow_schedule_agent_assignments`) which connects a Schedule to Agents and Models:
*   **Agent Connection:** Has a strict foreign key `agent_id` referencing `registry_ai_agents.id`.
*   **Model Connection:** Has a strict foreign key `model_id` referencing `registry_ai_models.id`.
*   **Tool Connection:** **Missing a strict join.** Tools (and Data Sources) are only loosely referenced via JSON arrays (`allowed_tools_json` and `allowed_data_sources_json`) within this assignment table rather than having their own structured mapping tables (e.g., no `workflow_schedule_tools` table).

### Summary of Traceability Gaps
While the system successfully links Agents and Models to a *scheduled intent* (via `WorkflowScheduleAgentAssignment`), **it breaks strict relational traceability at execution time**. If an agent is deleted or updated, a historical `WorkflowRun` has no structured way to point back to the exact version of the agent or tool that ran it, beyond whatever was serialized into the `context_json` payload.

B4. RBAC/ABAC Authorization Check

**Current Implementation:**
The application has a basic authorization service, but it is strictly Role-Based Access Control (RBAC). There is **no Attribute-Based Access Control (ABAC)** implemented. The system currently does not check context such as department, scope, or risk level when authorizing actions.

**Core Authorization Functions:**
1. **Permission-Based (Phase 0/1 Auth):** 
Found in `app/modules/auth/dependencies.py`. It simply verifies if the required string (e.g., `"policy.read"`) exists in the user's role-permission mapping.
```python
def require_permission(permission_code: str):
    def permission_dependency(current_user: User = Depends(get_current_user)):
        for role in current_user.roles:
            for permission in role.permissions:
                if permission.permission_code == permission_code:
                    return current_user
        raise HTTPException(
            status_code=403,
            detail=f"Not enough permissions. Requires: {permission_code}"
        )
    return permission_dependency
```

2. **Role-Based (Phase 2 Registry):**
Found in `app/modules/registry/routes.py`. It hardcodes specific role codes rather than relying on granular permissions or attributes.

```python
def require_read_roles(current_user, request_id: str):
```

B4. RBAC/ABAC Authorization Check

**Current Implementation:**
The application has a basic authorization service, but it is strictly Role-Based Access Control (RBAC). There is **no Attribute-Based Access Control (ABAC)** implemented. The system currently does not check context such as department, scope, or risk level when authorizing actions.

**Core Authorization Functions:**
1. **Permission-Based (Phase 0/1 Auth):** 
Found in `app/modules/auth/dependencies.py`. It simply verifies if the required string (e.g., `"policy.read"`) exists in the user's role-permission mapping.
```python
def require_permission(permission_code: str):
    def permission_dependency(current_user: User = Depends(get_current_user)):
        for role in current_user.roles:
            for permission in role.permissions:
                if permission.permission_code == permission_code:
                    return current_user
        raise HTTPException(
            status_code=403,
            detail=f"Not enough permissions. Requires: {permission_code}"
        )
    return permission_dependency
```

2. **Role-Based (Phase 2 Registry):**
Found in `app/modules/registry/routes.py`. It hardcodes specific role codes rather than relying on granular permissions or attributes.
```python
def require_read_roles(current_user, request_id: str):
    if current_user.role_code not in ["ADMIN", "GOVERNANCE_MANAGER", "APPROVER", "AUDITOR"]:

            message="Insufficient permission", error_code="FORBIDDEN", request_id=request_id
```
