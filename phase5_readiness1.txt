  - `escalation_sent_at` : `Column(TIMESTAMP(timezone=True), nullable=True)`
- **Escalation Resolver:** `ScheduleNotificationService._get_escalation_owner` (in `backend/app/modules/notifications/service.py`) checks schedule metadata `escalation_owner_id` or pulls `escalation_owner_user_id` from the schedule's owning `Department`.
- **API Surface / Triggering:** Escalation alerts are triggered as notification records stored in `workflow_notifications`:
  - SLA breaches (`notify_sla_breach`) sends notifications (`notification_type = "SLA_BREACHED"`, severity `CRITICAL`) to the escalation owner and `GOVERNANCE_ADMIN` users.
  - High risk outputs (`notify_high_risk_output`) sends notifications (`notification_type = "HIGH_RISK_OUTPUT"`, severity `CRITICAL`) to the schedule owner, `RISK_MANAGER`s, and `COMPLIANCE_OFFICER`s.
  - Run failures (`notify_run_failed`) sends notifications (`notification_type = "RUN_FAILED"`) to the owner and the escalation owner.

**Does any approval or escalation module support context hashes or idempotency keys?**
**NO.** 

Neither the legacy `approvals` table, the `workflow_schedule_approvals` table, nor the `workflow_notifications` table includes any context hash or request snapshot binding columns today.

**Impact for Phase 5:**
To implement the TOCTOU protection required by the Policy Binding and Agent Boundary specifications (ensuring that approvals and exceptions are bound to an immutable snapshot of the request), a context hash generation and validation column must be added to the new Phase 5 policy exception and approval models.

--------------------------------------------------------------------------------
5.1. Authorization Service and Permission Matrix Mapping
--------------------------------------------------------------------------------

**Current State:**
The authorization modules (`rbac_service.py`, `abac_service.py`, and `decision_service.py` in `backend/app/modules/authorization/`) are **fully implemented and active**. They are invoked directly by routers (e.g. `phase2_run_routes.py`) to enforce access boundaries on runs, outputs, and schedules.

- **`rbac_service.py`**: Resolves subject permissions/roles from the `permissions`, `roles`, `user_roles`, and `role_permissions` tables, supporting user permission checks (`check_permission`), role retrievals, and delegation checks (`has_active_delegation`).
- **`abac_service.py`**: Implements rule-based evaluation logic for workflows and schedules. It checks departments match, risk-level activation thresholds, maximum execution mode limits for assignments, output read sensitivity rank checks, and relationship owner verification.
- **`decision_service.py`**: Integrates both RBAC and ABAC evaluations. When evaluated, it generates authorization logs stored in the `workflow_authorization_decisions` table and publishes security logs (`AUTHORIZATION_DENIED` governance events) in the case of failures.

**Phase 5 Permission Mapping:**
- **Policy Admin:** Maps to `SUPER_ADMIN` or `GOVERNANCE_ADMIN` roles / legacy `policy.write` permission.
- **Policy Author:** Maps to `GOVERNANCE_ADMIN`, `RISK_MANAGER`, or `COMPLIANCE_OFFICER` roles / legacy `policy.write` permission.
- **Object Owner (Agent/Model/Tool/DataSource):** Checked dynamically by `abac_service.py:check_relationship_modification_access`, matching active `OWNER` records in `object_responsibilities`.
- **Approver (Schedule/Exception):** Verified dynamically by checking if the user is a member of the designated `ApprovalGroupMember` or has role `RISK_MANAGER`/`SUPER_ADMIN`/`COMPLIANCE_OFFICER` / legacy `approval.review` permission.
- **Auditor:** Maps to the `AUDITOR` role / legacy `audit.read` permission.
- **Runtime Service:** No distinct role exists; currently defaults to systemic `SYSTEM` actor context in the scheduler worker.

PHASE 5 READINESS REPORT (SECTION 6: CACHING INFRASTRUCTURE)
================================================================================

--------------------------------------------------------------------------------
6.1. Caching Layer Status and Invalidation
--------------------------------------------------------------------------------

**Does an existing cache layer exist?**
**Yes (In-Process Memory Cache).**

- **Implementation:** An in-process, thread-safe memory cache service is defined in `MemoryCacheService` (`backend/app/modules/relationship/cache_service.py`).
  - It wraps a standard Python dictionary under a threading lock (`threading.Lock()`).
  - It associates cache entries with UTC expirations (`expires_at`) to support custom time-to-live settings (defaults to 300 seconds).
- **Tenant-based Invalidation:** It includes an `invalidate_tenant(tenant_id)` method which removes all cached keys containing the target tenant UUID string.
- **Active Usage:** 
  - Used in the relationship module (`backend/app/modules/relationship/api.py`) to cache graph lineage queries (`GET /api/relationship/lineage` and `GET /api/relationship/impact-analysis`).
  - Automatically invalidated on any relationship write mutations (like creation, suspension, activation, or approvals) by calling `MemoryCacheService().invalidate_tenant(tenant_id)`.
- **Redis Cache:** Although Redis is configured and active as the Celery broker/backend (`backend/app/celery_app.py`), **it is not used as a shared data cache layer** anywhere in the python backend today.

**Considerations for Phase 5:**
While the local `MemoryCacheService` meets sub-200ms latency targets (local operations run sub-1ms), it is an in-process cache. In a multi-instance production environment, this cache will not synchronize invalidation events across backend service instances. If distributed cache consistency is required, a Redis-backed caching service (leveraging the existing Redis infrastructure) should be introduced for Phase 5 policy bindings and exceptions.

--------------------------------------------------------------------------------

**Is `scheduler_worker.py` the only real async worker in the codebase?**
**NO.**

1. **`SchedulerWorker`** (`backend/app/workers/scheduler_worker.py`): 
   - **Purpose:** Polls `workflow_schedules` for active due items.

2. **`OutboxDispatcher`** (`backend/app/modules/events/dispatcher.py`):
   - **Purpose:** Polls `event_outbox` for pending/failed outbox records to publish to the event bus.
   - **Execution:** Runs as a standalone async process. Exposes a health server on port `8082`.

10.2. DB-Enforced Append-Only Immutability
--------------------------------------------------------------------------------

**Has append-only enforcement (DB triggers rejecting UPDATE/DELETE) been used?**
**Yes (Precedent exists).**

- **Implementation:** The database defines a PostgreSQL PL/pgSQL function called `prevent_update_delete()` which aborts any query targeting those operations:
  ```sql
  CREATE OR REPLACE FUNCTION prevent_update_delete()
  RETURNS TRIGGER AS $$
  BEGIN
      RAISE EXCEPTION 'Updates and Deletes are not allowed on this table.';
      RETURN NULL;
  END;
  $$ language 'plpgsql';
  ```
- **Application:** This is applied as a trigger `trg_immutability_audit_events` `BEFORE UPDATE OR DELETE ON audit_events` to make it append-only.
- **Loading mechanism:** The trigger definition is stored in `database/ddl/V2_FIX_003__missing_triggers.sql` and loaded dynamically during application startup via a lifespan hook in `backend/app/main.py`.
- **Phase 5 Target:** This exact trigger pattern (`prevent_update_delete`) can be applied `BEFORE UPDATE OR DELETE` to make the new Phase 5 `governance_events` table and activated `policy_versions` append-only.
